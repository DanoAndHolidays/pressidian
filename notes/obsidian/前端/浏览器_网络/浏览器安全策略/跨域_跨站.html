跨域

协议，域名，端口，三者有一不一样，就是跨域 案例一：www.baidu.com 与 zhidao.baidu.com 是跨域

目前有三种最常见的解决方案：

CORS跨域资源共享&跨域请求流程

Access-Control-Allow-Origin: https://example.com  # 允许的源
Access-Control-Allow-Methods: GET, POST, PUT      # 允许的方法
Access-Control-Allow-Credentials: true            # 是否允许携带凭证
Access-Control-Max-Age: 86400                     # 预检请求缓存时间
Access-Control-Allow-Headers:
Access-Control-Expose-Headers:

	location /api/ {
	
    # 允许跨域的源（生产环境建议替换 * 为具体域名，或使用变量动态匹配）
    add_header 'Access-Control-Allow-Origin' '*' always;
    
    # 允许的请求方法
    add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE, OPTIONS' always;
    
    # 允许的请求头
    add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization, X-Requested-With' always;
    
    # 是否允许携带凭证（如 Cookie）
    add_header 'Access-Control-Allow-Credentials' 'true' always;

    # 处理预检请求（OPTIONS），直接返回 204 状态码

        add_header 'Access-Control-Max-Age' 1728000; # 预检请求缓存时间
        add_header 'Content-Type' 'text/plain; charset=utf-8';
        add_header 'Content-Length' 0;
        return 204;
    }
    
    # 你的正常业务代理或处理逻辑...

一个跨域请求发起后的完整过程，其实是浏览器、前端、服务器三方紧密配合的结果。我们可以把这个过程拆解为以下几个关键阶段：

浏览器自动识别与拦截

当你在前端（比如运行在 http://localhost:3000 的网页）通过 Ajax、Fetch 等方式发起一个请求，去访问不同源的接口（比如 https://api.example.com）时，浏览器会自动识别出这是一次跨域请求。

此时，浏览器会在该请求的 HTTP 头部中，自动添加一个 Origin 字段，用来告诉服务器：“我是从哪个源（协议+域名+端口）发起的请求”。
例如：
Origin: http://localhost:3000

判断请求类型（简单请求 vs 预检请求）

浏览器会根据请求的方法和头部信息，将跨域请求分为两类，它们的后续处理流程截然不同：

  • 简单请求 (Simple Request)：必须同时满足以下条件：
    1. 请求方法是 GET、POST 或 HEAD。
    2. 请求头仅包含安全的字段（如 Accept、Accept-Language、Content-Language 等）。
    3. Content-Type 仅限于 text/plain、multipart/form-data 或 application/x-www-form-urlencoded。
  • 预检请求 (Preflight Request)：只要不满足简单请求的任意一个条件（例如使用了 PUT、DELETE 方法，Content-Type 为 application/json，或者带了自定义的 Authorization 头部），就会被判定为预检请求。
服务器响应与浏览器校验

简单请求

  1. 直接发送：浏览器会直接跳过询问，把真实的业务请求发送给服务器。
  2. 服务器响应：服务器正常处理业务逻辑，并在返回的 HTTP 响应头中带上 CORS 相关的字段（比如你之前配置的 Access-Control-Allow-Origin）。
  3. 浏览器校验：浏览器接收到响应后，会检查响应头中的 Access-Control-Allow-Origin 是否包含当前页面的 Origin。
    • 校验通过：浏览器将服务器返回的数据交给前端的 JavaScript 处理。
    • 校验失败：浏览器直接在控制台抛出 CORS 跨域错误，前端无法获取到响应数据（即使服务器返回了 200 状态码）。

预检请求（多了一步“探路”）

  1. 发送预检 (OPTIONS)：在发送真实的业务请求之前，浏览器会先自动发起一个 OPTIONS 方法的请求，去“探探路”。这个请求会带上 Access-Control-Request-Method（告诉服务器我真实请求想用什么方法）和 Access-Control-Request-Headers（告诉服务器我真实请求带了哪些自定义头）。
  2. 服务器批准：服务器收到 OPTIONS 请求后，需要检查自己是否允许该跨域操作，并返回对应的 Access-Control-Allow-* 响应头（如 Access-Control-Allow-Methods, Access-Control-Allow-Headers）。
  3. 发送真实请求：只有当浏览器收到 OPTIONS 的批准响应后，才会紧接着发出真实的业务请求（如 PUT 或 POST）。
  4. 最终校验：浏览器再次校验真实请求的响应头，决定是否将数据交给前端。
核心认知与避坑提醒
  • 请求其实“发出去”了：跨域限制是浏览器的安全机制。这意味着，即使前端报了跨域错误，你的请求其实已经成功到达了服务器，服务器也正常处理并返回了数据。只是浏览器在拿到响应后，发现响应头不符合 CORS 规范，从而“扣留”了数据，不让前端 JS 读取。
  • Cookie 等凭证的特殊限制：如果你的跨域请求需要携带 Cookie（前端设置 credentials: 'include'），服务器必须返回 Access-Control-Allow-Credentials: true。但此时，Access-Control-Allow-Origin 绝对不能使用通配符 *，必须明确指定前端的具体域名，否则浏览器会直接拦截。
  • 预检缓存优化：每次复杂请求都要先发一次 OPTIONS ，会带来额外的网络延迟和开销。服务器可以设置 Access-Control-Max-Age 头部，浏览器会将预检结果缓存起来，在指定的有效期内，对相同 URL 和请求头组合的后续请求将不再发送 OPTIONS 预检请求，从而显著提升接口性能。

反向代理服务器

Reverse Proxy，在 nginx/traefik/haproxy 等反向代理服务器中设置为同一域名。前端向后端发送请求时会先经过代理服务器，代理服务器再向后端发送请求，后端反回数据给前端，前端本身是不知道的，也就是反向代理服务器对于前端是透明的。

Reverse Proxy是一种位于客户端和实际服务器之间的服务器，它接收客户端的请求，然后将这些请求转发给后端服务器，并将后端服务器的响应返回给客户端。客户端并不知道它正在与反向代理通信，而认为是在直接与目标服务器通信。

客户端 → 反向代理 → 后端服务器
客户端 ← 反向代理 ← 后端服务器
主要功能与用途
  1. 负载均衡
# Nginx 配置示例
upstream backend {
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=2;
    server 192.168.1.12:8080 weight=1;
}

server {
    location / {
        proxy_pass http://backend;
    }
}
  1. 缓存加速
  • 缓存静态资源（图片、CSS、JS等）
  • 减少后端服务器压力
  • 提高响应速度
  1. 安全防护
  • 隐藏后端服务器真实IP
  • 提供SSL/TLS终止
  • 防御DDoS攻击
  • Web应用防火墙（WAF）
  1. SSL终端
server {
    listen 443 ssl;
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    
    location / {
        proxy_pass http://backend_server;
        proxy_set_header Host $host;
    }
}
  1. 内容压缩
gzip on;
gzip_types text/plain text/css application/json;
  1. 统一入口点
  • 多个服务使用同一域名和端口
  • 基于路径或域名的路由
常见反向代理软件
  1. Nginx
server {
    listen 80;
    server_name example.com;
    
    location /api/ {
        proxy_pass http://api_backend;
        proxy_set_header X-Real-IP $remote_addr;
    }
    
    location /static/ {
        proxy_pass http://static_backend;
        expires 30d;
    }
}
  1. Apache
<VirtualHost *:80>
    ProxyPreserveHost On
    ProxyPass /api http://backend-api:8080/
    ProxyPassReverse /api http://backend-api:8080/
</VirtualHost>

frontend web_front
    bind *:80

JSONP

它有个限制，只能用GET请求，并且要求返回JavaScript。这种方式跨域实际上是利用了浏览器允许跨域引用JavaScript资源：

<html>
<head>
    <script src="http://example.com/abc.js"></script>
    ...
</head>
<body>
...
</body>
</html>

JSONP通常以函数调用的形式返回，例如，返回JavaScript内容如下：

foo('data');

这样一来，我们如果在页面中先准备好foo()函数，然后给页面动态加一个&lt;script&gt;节点，相当于动态读取外域的JavaScript资源，最后就等着接收回调了。
