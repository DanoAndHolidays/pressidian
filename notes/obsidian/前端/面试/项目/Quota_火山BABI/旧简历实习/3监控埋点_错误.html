3监控埋点&错误

前端稳定性治理以及监控埋点

你参与前端稳定性治理，给核心链路做监控埋点，请讲讲你的埋点设计思路、埋点类型，以及如何评估可用性提升效果？ 满分答案： 前端稳定性是大厂前端重点工作，我负责的是审批流、配额申请、账号操作这三条核心用户链路的埋点落地。

  1. 埋点设计思路 先梳理用户完整操作链路，区分核心行为和次要行为，优先保障业务关键路径；埋点做到无侵入、低性能损耗，不影响页面正常交互。同时区分不同上报类型，拆分数据用途。

  2. 主要埋点类型

    • 行为埋点：记录用户点击、提交申请、切换页面等操作，统计链路转化率，看用户卡在哪个环节；
    • 异常埋点：捕获全局JS报错、接口请求失败、资源加载失败，上报错误信息、堆栈、设备、用户ID；
    • 性能埋点：记录页面首屏加载、接口耗时、交互响应耗时，监控页面性能波动。

  3. 效果评估方式 埋点上线后，我们通过监控平台查看核心指标：页面JS错误率、接口失败率、链路失败率。对比埋点前后的数据，能清晰看到高频错误被逐一修复后，整体错误率持续下降；同时结合用户反馈工单，业务侧的线上问题反馈也明显减少，证明链路可用性得到有效提升。

面试官问：“你在实习期间做过哪些有亮点的工作？”

你的回答： “在实习期间，我主要负责了内部办公系统‘审批单提交’模块的稳定性治理。当时我们发现一个痛点：用户在点击提交时，如果遇到网络异常或必填项漏传，前端没有正确捕获错误，导致页面没反应，用户就会疯狂重复点击，产生很多脏数据。

为了解决这个问题，我做了两件事： 第一，我在项目的 Axios 请求封装里加了全局拦截兜底。只要接口报错，就会统一弹出明确的 Toast 提示，彻底解决了‘静默失败’的问题，消灭了相关的客诉。 第二，为了让系统状态透明化，我在核心按钮上接入了自定义埋点。每次点击和报错都会带上具体的 error_msg 上报。上线后，我们通过监控看板就能实时看到报错率。有一次后台改了校验规则导致提交失败率飙升，我就是通过埋点第一时间发现并通知后端修复的，避免了更大范围的影响。

虽然这只是个小优化，但我觉得它让系统的状态从‘黑盒’变成了‘白盒’，大大提升了我们排查问题的效率。”

回答：我针对审批流、配额申请、账号操作三大核心链路做埋点。 设计思路：优先保障核心业务路径，做到埋点无侵入、低性能损耗，区分上报类型。 埋点分为三类：行为埋点记录用户操作，统计链路转化率；异常埋点捕获JS报错、接口失败、资源异常；性能埋点监控首屏、接口、交互耗时。 效果评估：通过监控平台查看JS错误率、接口失败率、链路失败率等核心指标，对比埋点前后数据，同时结合用户反馈工单，错误率下降、问题反馈减少，证明链路可用性提升。

团队使用自研监控SDK，如何解决弱网埋点丢失、重复上报、离线用户上报三大问题？错误如何分级与闭环？

我们使用内部自研监控SDK：

  1. 弱网/断网丢失：上报失败的埋点存入localStorage，网络恢复后批量补发，同时合并同类埋点减少请求；
  2. 重复上报：每条埋点生成唯一ID，服务端做幂等去重，前端对高频上报事件做节流；
  3. 离线上报：监听online事件，联网后自动推送离线缓存数据。
  • 使用自研 SDK（类似 Sentry），在 componentDidCatch / window.onerror / unhandledrejection 捕获错误
  • 自动上报：错误堆栈、用户操作路径（录屏或事件序列）、网络请求、用户 ID、浏览器信息
  • 关键路径手动埋点：trackEvent('quota_apply_click')、trackTimer('quota_export_duration')

错误分级与闭环：分为P0（全站瘫痪）、P1（核心链路异常）、P2（局部功能问题）、P3（样式文案问题）。监控平台自动聚合错误并分配负责人，我每日查看错误报表，修复后持续观察3天，错误率归零才算闭环。

AI工具是否误导过你的排错方向？举例说明，同时讲下AI生成代码的隐性风险与管控手段

AI代码存在四大隐性风险：逻辑漏洞、性能问题、TS类型不严谨、不符合团队编码规范。我的管控方式：核心业务逻辑人工主导，AI仅辅助改写；高频交互代码人工做性能审查；开启TS严格校验，修正隐式any等问题；代码统一格式化、人工核对规范。我始终将AI作为效率工具，核心决策与风险把控由人工完成。

AI Skill + MCP 工具&错误定位

团队使用 AI Skill、MCP 工具分析线上日志，你具体是如何借助这些AI工具定位、修复高频JS错误的？和传统人工排错相比有什么优势？ 满分答案： 传统排错方式是：先看原始日志、分析报错堆栈、复现问题，整个流程繁琐，尤其是高频、偶现的JS错误，人工筛选效率极低。

我们团队的AI Skill + MCP工具主要用来智能聚合日志、解析报错堆栈、关联代码片段、给出修复建议，我的使用流程：

  1. 筛选时间段、对应页面的错误日志，AI工具自动把同类型报错聚合分组，不用我逐条筛选重复日志；
  2. AI解析JS报错堆栈，自动关联到项目源码文件、对应代码行，快速定位出错位置；
  3. 针对语法错误、类型错误、空指针这类常见问题，工具会直接给出修复思路和参考代码；
  4. 我结合业务场景验证建议，再落地修复，修复后重新观察日志，确认对应错误不再复现。

对比人工排错，优势很明显： 第一，效率大幅提升，AI聚合日志、解析堆栈，省去大量重复筛选工作； 第二，降低偶现问题排查难度，很多线上偶现Bug本地难以复现，AI结合海量日志能还原报错上下文； 第三，新人友好，像我实习阶段对庞大项目源码不熟，工具能快速关联代码，缩短上手排错的时间。

当然AI给出的建议只是参考，最终还是需要我结合业务逻辑校验、自测，保证修复不会引入新问题。

  • MCP（Model Context Protocol）：一种让 AI 能调用外部工具（如日志查询、代码库检索）的协议。我们搭建了一个内部 AI Bot，配置了 Skill：
    • query_logs：根据错误指纹查询最近 1 小时的错误日志样本
    • get_source_code：根据错误堆栈中的文件路径和行号，从 Git 仓库中拉取对应代码片段
    • suggest_fix：将错误 + 代码上下文发送给 LLM，生成修复建议
  • 实际使用：当线上错误率飙升，我在 AI Bot 中输入错误聚合 ID，它会自动拉取日志样本，定位到是 Cannot read property 'id' of undefined，然后显示是某个组件中 data.user 在初次渲染时为 null。AI 建议添加可选链 data.user?.id 或使用 Skeleton 等待数据。

我修复的高频错误案例：

  • 错误：TypeError: Cannot read properties of undefined (reading 'map') 出现在配额审批列表
  • 定位：AI 工具显示错误来自 ApprovalList.tsx 第 23 行，请求的 data.list 在某些边界条件（无数据时）返回 undefined 而非 []
  • 修复：在初始 state 中设置 list: []，并在请求落 catch 时也置为 []，同时增加空态 UI

应急场景压力题

如果线上突然出现核心页面大面积JS报错、页面白屏，结合你的实习经验，说下你的应急排查和处理流程？ 满分答案： 遇到线上大面积报错/白屏，我会按照止损→排查→修复→复盘四步快速处理：

  1. 第一步：紧急止损（优先保障业务） 第一时间同步组长和团队，确认是否是版本发布导致；如果是刚上线的版本，立刻执行版本回滚，先恢复线上正常服务，把影响降到最低。

  2. 第二步：快速定位根因 查看监控平台、AI日志工具，抓取全局报错信息：

    • 看报错类型：是语法错误、资源加载失败、接口4xx/5xx，还是第三方依赖异常；
    • 看影响范围：是全用户还是部分用户、全页面还是单个模块；
    • 结合Git提交记录，核对本次上线改动的代码、依赖包、配置文件。

  3. 第三步：修复与灰度验证 定位问题后本地复现、编写修复代码；先在测试环境验证，再走小流量灰度发布，确认错误消失后全量上线。

  4. 第四步：事后复盘 记录Bug根因、触发条件，补充单元测试、增加前置校验；如果是上线流程问题，同步团队优化MR审核、预发环境测试环节，避免同类问题重复出现。
