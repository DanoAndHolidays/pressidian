1组件重构&权限面板

重构过程中使用了哪些React Hooks，各自作用是什么？遇到过哪些坑，如何解决？

  1. 重构时有没有抽离自定义Hook？举例说明抽离了哪些？
  • useState：管理列表筛选条件、权限面板的临时状态
  • useEffect：监听筛选条件变化，自动重新拉取列表数据；组件挂载时获取权限树
  • useCallback：避免子组件不必要的重渲染，比如将 handleSearch 传给子组件时包裹
  • useMemo：对列表数据进行过滤/排序等昂贵计算时使用
  • 自定义 Hook：我封装了 usePermission（接收权限标识，返回 boolean）、useExportWithPagination（封装分页导出逻辑，返回 startExport, progress, data）

2. 自定义 Hook 的实际代码示例（口述）
以 usePermission 为例：

 function usePermission(permissionId: string) {
   const permissions = useSelector(state => state.user.permissions);
   return useMemo(() => permissions.includes(permissionId), [permissions, permissionId]);
 }

3. 闭包陷阱的例子与解决
有一次在 useEffect 中使用了 setInterval，依赖了外部变量 count，但因为闭包捕获的是旧值，导致计时器内读不到最新 count。
解决方法：使用 useRef 保存最新值，或者用 useReducer 保证每次拿到最新 state。

回答：核心使用了useState、useEffect、useCallback、useMemo、useRef五个钩子。

  • useState：管理搜索关键词、筛选项、面板显隐等本地状态；
  • useEffect：监听筛选/搜索条件变化自动请求列表数据，组件卸载时取消请求，避免内存泄漏；
  • useCallback：缓存事件回调函数，配合React.memo减少子组件无效重渲染；
  • useMemo：缓存多条件筛选后的计算结果，提升渲染性能；
  • useRef：获取DOM元素实现搜索框聚焦，同时存储历史状态用于数据对比。

在 useEffect 中调用了 setState，并将 state 作为依赖，导致死循环。

解决方案：要么去掉该依赖（用 setState 的函数形式 setCount(prev =&gt; prev+1)），要么判断数据是否真的变化了再 set。

实操中遇到两个典型问题：一是useEffect依赖项缺失或冗余，导致逻辑执行异常，我严格遵循ESLint Hook规则，拆分纯函数精简依赖数组；二是闭包陷阱，回调拿到旧状态，解决方案是补全依赖项，或用useRef保存最新状态。

重构时是否抽离自定义Hook？举例说明，落地遇到了哪些问题及解决方案

回答：我按照单一职责拆分了useSearch、useFilter、usePermissionPanel三个自定义Hook，分别封装搜索、筛选、面板控制逻辑，大幅精简业务组件代码。

实现中遇到了状态共享污染、依赖项泛滥、TS类型推导异常等问题吗？如何解决？

落地踩了三个坑：一是多个组件复用Hook时出现状态污染，原因是Hook内部持有全局状态，我调整设计，让状态由调用方传入，保证多实例状态隔离；二是嵌套useEffect导致依赖项泛滥，我抽离纯函数、使用useEvent精简依赖；三是TS对自定义Hook类型推导异常，通过显式接口、泛型约束修复类型问题。

如何封装一个能拿到最新值的 useRef 而不触发渲染？

useRef 的 .current 变化不会触发重渲染，适合存储 timerId、上一次的值。封装 usePrevious 就是利用这个原理。

你只改Hooks、加TS，只是基础语法，没有技术深度

单纯语法替换确实偏向基础，但本次重构核心价值在于风险防控&鉴权。首先我通过自定义Hook、组件分层解决了代码臃肿、耦合严重的问题，提升项目可维护性；

其次TS不只是简单加类型，而是完成全链路类型约束、数据清洗与类型映射，从源头减少线上Bug；

最后结合业务完成交互兼容、异常兜底、性能优化。

语法只是工具，解耦、健壮性、长期可维护性，才是工业级前端开发的核心目标。

介绍下重构火山账号管理筛选、搜索组件的业务背景、重构目标与整体思路 🌟

搜索组件就是input的值班计划组件，原先没有权限校验等功能，现在对这里进行了升级。主要是为了配合新的业务场景，就将这里的input抽取出来单独的封装为了一个单独的组件，同时基于TS定义接口、枚举、组件入参类型，从编码阶段规避错误。经过我两次迭代目前实现了：

  • 自定义组件布局样式，便于通过props来动态调整组件的大小以及布局
  • 添加了完整的权限校验，鉴权逻辑，接受父组件的控制，对于没有权限的用户，禁止点击
  • 对于非法的值班计划进行实时校验，结合防抖以及竞态问题一方面是优化性能，另一方面是防止出现先发出的请求后返回，导致组件展示的值班计划与校验的值班计划不是一个，出现错位的问题
  • 针对不同环形（boe、ppe与线上环境，经行了专门的区分）

这里就说是啊，添加了新字段，前端加了些逻辑。。。

如果筛选条件有几十个，你怎么管理？

回答：当前列表单页数据仅200条以内，配合分页器，常规渲染完全满足性能要求。且内部后台优先保证稳定性与可维护性，自研虚拟列表会提升复杂度、拉长排期，收益很低，因此暂时未落地。 若后续数据涨到10万条，分三步优化：第一，细化组件粒度，强化memo浅比较，优化防抖逻辑；第二，接入团队通用虚拟列表组件；第三，将复杂筛选逻辑下沉至服务端，前端仅做展示。

重构方案：

  1. 统一状态管理：使用 useReducer 管理筛选表单状态，action 类型包括 SET_FIELD、RESET、SET_PAGE。
  2. 防抖 + 竞态处理：
    • 搜索输入框使用 useDebounce 自定义 Hook，延迟 300ms 触发。
    • 每个请求带一个 requestId（如 Date.now()），在 useEffect 的 cleanup 中标记过期，响应回来时对比是否是最新的请求。
  3. URL 同步：使用 useSearchParams（React Router v6）将筛选条件序列化到 URL，页面初始化时从 URL 读取并回填表单。
  4. TypeScript 类型设计：
     interface FilterParams {
   accountName?: string;
   roleId?: string;
   status?: 'active' | 'inactive' | 'pending';
   page: number;
   pageSize: number;
 }
 type FilterAction =
   | { type: 'SET_FIELD'; field: keyof FilterParams; value: any }
   | { type: 'RESET' };

3. **性能优化**：使用 `React.memo` 包裹每个筛选子组件，`useCallback` 传递 onChange 避免重渲染。

**追问：如果后端接口只支持分页和单字段排序，你要做多字段排序怎么办？**
 前端维护一个 `sortBy` 数组，每次请求前拼接成后端约定的格式（如 `sort=name,-createTime`），或者在前端对已拉取的数据进行多级排序（仅适合小数据量）。

### 重构为何搭配TypeScript？做了哪些类型定义，TS带来了哪些收益？
为什么重构时一定要搭配 TypeScript？结合这个筛选/搜索组件，说说你做了哪些类型定义，TS 带来了哪些实际收益？
**满分答案：**
这个模块是内部核心后台，对接后端账号、权限、筛选条件等复杂数据，接口字段多、枚举值多，纯JS开发很容易出错，所以团队要求重构必须接入TS。

我主要做了这几类类型定义：
1. 定义**接口类型**：账号列表项、搜索入参、多维度筛选条件（部门、账号状态、创建时间等）；
2. 定义**枚举类型**：账号状态、权限等级、筛选标签类型，替代硬编码字符串；
3. 定义**组件Props/Emits类型**：约束父子组件传参的格式、必填项，杜绝传参漏传、错传；
4. 定义通用工具类型：针对分页、列表返回数据做通用泛型，复用在多个后台组件中。

实际收益非常直观：
第一，**编码阶段报错拦截**，VSCode可以实时提示字段不存在、类型不匹配，很多低级错误在本地开发就被发现，不用等到测试或线上暴露；
第二，**接口文档作用**，后续同事迭代组件时，通过类型定义就能看懂数据结构和入参要求，不用反复查接口文档；
第三，**重构更安全**，大规模修改组件逻辑时，TS会全局校验类型联动，避免改一处引发多处隐性问题。

**回答**：该模块对接复杂的账号、权限数据，接口字段与枚举繁多，纯JS易引发线上问题，因此团队要求全量接入TS。
我主要定义四类类型：账号列表、搜索入参、筛选条件等**接口类型**；账号状态、权限等级等**枚举类型**；组件Props约束父子传参；以及分页、列表通用**泛型工具类型**。
实际收益很明显：第一，编码阶段拦截类型错误，提前规避线上问题；第二，类型定义等同于接口文档，降低团队协作沟通成本；第三，大规模重构时，TS全局校验类型联动，保证重构安全性。

问题8：使用TS时，针对后端不规则数据、树形权限数据，用到了哪些高级类型与适配方案？
**回答**：我使用了泛型、联合类型、交叉类型、`Pick/Omit/Record`等TS高级类型。
1. 封装全局分页泛型`PageList&lt;T&gt;`，复用所有列表结构；
2. 用联合类型管理多分支筛选状态，做类型收窄；
3. 针对后端不规则字段，先编写数据清洗函数标准化数据，再绑定TS接口，谨慎使用类型断言；
4. 定义**递归接口**描述权限树形结构，用`Readonly`防止静态数据被篡改；
5. 针对前后端枚举值格式不一致问题，编写双向转换函数，保证类型对齐。

### 权限编辑页面的相关问题
我们的权限控制粒度比较的粗，在权限配置页面的路由入口处，如果没有权限，就会直接禁止点击，部分的页面虽然不可以配置，但是可以查看，那这里的就是一个页面级的权限控制了，然后，如果用户有我们权限配置的页面路由地址的话，他直接访问，不去点击的话也是无法直接进行配置的，每次进入这个组件的时候，会去获取当前角色的权限。在配置页面上会有个特殊的配置项，这个必须要求你是根组件的管理员，才可以点击，就算你是当前业务的管理员也不可以点击，这个的话我们是去校验当前的角色是否是根组件的管理员

页面级（入口位置）、组件级（查看但是不能编辑）、按钮级（根组件管理员的按钮）的权限控制，没有做动态的过滤路由列表，主要是为了保证入口的一致性
